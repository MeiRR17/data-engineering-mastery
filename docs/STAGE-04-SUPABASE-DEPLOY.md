# Stage 04 — optional DataPulse deployment to an isolated Supabase sandbox

[Local PostgreSQL lab](../labs/04-postgres/README.md) · [DataPulse](../projects/datapulse/README.md) · [Official Supabase documentation](https://supabase.com/docs/)

**Start with the local PostgreSQL 17 lab**. Passing Docker migration/RLS tests does not prove Supabase Auth, Data API exposure or hosted role isolation. Only use a **new, learner-owned, explicitly authorized and budget-limited** Supabase sandbox. Never point exercises at an existing organization or production database.

## Controlled deployment procedure

1. Confirm the **actual** CLI version and supported commands, rather than copying an obsolete command signature:

~~~bash
supabase --version
supabase --help
supabase migration --help
supabase db --help
~~~

2. Create an isolated local working directory. If needed, run `supabase init` and create a migration with a documented current CLI command such as `supabase migration new datapulse_initial`.
3. Inspect [the source migration](../projects/datapulse/database/001_init.sql), then copy its reviewed SQL into the migration file generated by the CLI. **Do not deploy the lab's `bootstrap.sql`**: it creates simulated roles for an isolated Docker exercise.
4. Before linking or pushing any migration, verify the selected project, account, region, billing limits, exposure settings and owner approval.
5. Check current Supabase Data API exposure settings **in addition to** database `GRANT` and row-level security. The mere existence of an object in `public` does not prove how API access has been configured.
6. Keep publishable client keys subject to proper public read authorization. Secret/service-role keys belong only in approved backend or CI secret storage, **never in browser JS, screenshots, chat or Git**.
7. **Positive smoke tests:** allowlisted read access to approved curated data/views, secure synthetic ingestion from a backend and UTC-correct aggregates.
8. **Negative smoke tests:** anonymous users cannot read `raw_earthquakes` or `ingest_runs`, insert/delete curated records or execute privileged ingest functions.
9. Exercise replay, a late correction, malformed input and an atomic pre-commit rollback in the isolated sandbox. Inspect security/performance advisors.
10. Record migration path, commit SHA, environment identity (not credentials), test commands, redacted outputs, expected cost and cleanup plan. Claim `deployed` only after an actual authorized remote smoke test.

## Common problems

| Symptom | Investigate |
| --- | --- |
| HTTP 401/403 | API key, session, GRANT, RLS and Data API exposure |
| Query returns no rows | Policy, fixture data, filters and timezone |
| A view leaks private rows | `security_invoker`, grants and object ownership |
| Raw/curated mismatch | Ingestion transaction and `source_updated_at` revision policy |
| Migration fails | Existing migration history and schema drift |
| Unexpected cost | Compute, storage, API calls, scheduled jobs and backups |

**Exit evidence:** locally tested after the PostgreSQL CI run; integration-tested/deployed only after the **real, approved Supabase** checks above. Do not run destructive `db reset` commands against valuable or shared data.
